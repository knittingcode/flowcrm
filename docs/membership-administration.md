# Membership administration

How an organization's ADMIN adds existing users, changes their roles and
removes them through the API (FCRM-FND-010C). The design and its reasons
are in [ADR-020](architecture/adr/ADR-020-membership-administration.md)
(proposed); sessions, CSRF and tenant authorization in
[authentication](architecture/authentication.md); the contract is
[`backend/openapi.yaml`](../backend/openapi.yaml).

All examples use synthetic data: `example.test` addresses and UUIDs of the
form `00000000-0000-7000-8000-…`. Real IDs are UUIDv7 values generated by
the server.

## Who can do what

`App\Organizations\Domain\RolePolicy` is the only source of the role
matrix. Each role lists its permissions explicitly; nothing is inherited
and anything not listed is denied.

| Permission | ADMIN | MANAGER | REP |
|---|---|---|---|
| `organization.view` | yes | yes | yes |
| `membership.list` (name, role) | yes | yes | yes |
| `membership.view_email` | yes | yes | no (provisional) |
| `membership.add` | yes | no | no |
| `membership.change_role` | yes | no | no |
| `membership.remove` | yes | no | no |

- The permissions of the current membership are returned with the
  memberships (`GET /api/v1/auth/session`, `GET /api/v1/me`,
  `GET /api/v1/organizations/{organizationId}`). The SPA uses them only to
  show controls; the API decides every request itself.
- The rule that an organization keeps at least one active ADMIN applies to
  everyone, including an ADMIN who demotes or removes themselves.
- Users are created and passwords reset only by the platform operator on
  the console (see [operator console](#operator-console)). There is no
  invitation and no self-registration.

## Workflows

### Add an existing user

1. The ADMIN enters the e-mail address of an existing user and a role
   (`ADMIN`, `MANAGER` or `REP`).
2. The address is matched case-insensitively. The answer contains the
   address as stored, not as entered.
3. The new member can use the organization from their next request; the
   change is audited as `membership.added` with `{"role": …}`.

Refused: an address without a user account (422 `UNKNOWN_USER`), a user who
already has a membership in the organization, active or removed (409
`MEMBERSHIP_EXISTS`). A removed member cannot be added again.

### Change a role

1. The ADMIN selects a new role for an active member.
2. The answer is the member with the role now held. The same role again is
   a 200 without a change and without an audit event; any other change is
   audited as `membership.role_changed` with `{"roleFrom": …, "roleTo": …}`.
3. The member gets the permissions of the new role from their next request.

Refused: demoting the only active ADMIN, also oneself (409 `LAST_ADMIN`).
An ADMIN who demotes themselves (with another ADMIN left) loses the
administration permissions immediately.

### Remove a member

1. The ADMIN removes an active member. The membership becomes `REMOVED`;
   the row stays and is not shown in the member list any more.
2. The removed user's next request to the organization is a 404, the same
   answer as for an organization that does not exist. The change is audited
   as `membership.removed` with `{"role": …}`.

Refused: removing the only active ADMIN, also oneself (409 `LAST_ADMIN`).
A repeated removal is a 404.

## HTTP examples

### Requirements for unsafe requests

`POST`, `PATCH` and `DELETE` under `/api` pass
`App\Shared\Http\Security\RequestOriginGuard` before the firewall:

| Header | Rule | Otherwise |
|---|---|---|
| `Content-Type: application/json` | required for a request with a body (`POST`, `PATCH`); `DELETE` has no body and needs none | 415 `unsupported-media-type` |
| `Origin` | must equal the request's own origin (scheme, host and port); without `Origin` the origin of `Referer` must; without both the request is refused | 403 `csrf-invalid` |
| `Sec-Fetch-Site` | optional; when sent, it must be `same-origin` | 403 `csrf-invalid` |
| `X-CSRF-Token` | the session's CSRF token (`csrfToken` of the login, `GET /api/v1/auth/session` or `GET /api/v1/me` answer) | 403 `csrf-invalid` |
| `Cookie` | the session cookie: `flowcrm_sid` in local development (plain HTTP on `127.0.0.1`), `__Host-flowcrm_sid` everywhere else | 401 `unauthenticated` |

There is no CORS: the API is called from the SPA's own origin. The examples
below use the development edge at `http://127.0.0.1:8080`; the port is
chosen when the stack starts (`make url` in
[development environment](dev-environment.md)). Elsewhere the origin is
`https://` and the cookie is `__Host-flowcrm_sid`.

With curl, which sends no `Origin` of its own, a session can be opened and
its token read like this (`jq` is used only to extract the token):

```console
$ base=http://127.0.0.1:8080
$ curl -s -c jar -b jar -H "Origin: $base" -H 'Content-Type: application/json' \
    -d '{"email":"ada@example.test","password":"…"}' "$base/api/v1/auth/login" | jq -r .csrfToken
```

Then every unsafe request sends `-b jar -H "Origin: $base" -H "X-CSRF-Token: $token"`,
and `-H 'Content-Type: application/json'` when it has a body.

Every answer carries `X-Request-Id`; a problem document repeats it as
`requestId`. Problem documents are `application/problem+json` with exactly
the members `type`, `title`, `status`, `instance` (the request path),
`requestId` and, for 409 and 422, `errors`. The test client checks every
answer against `backend/openapi.yaml`.

In the examples the ADMIN Ada Example (`ada@example.test`) administers the
organization `00000000-0000-7000-8000-0000000000a1`.

**The audit event cannot be written:** nothing is changed and the answer is
a 500 with type `/problems/internal-error` and the `requestId` of the
`X-Request-Id` header.
<!-- verified by MembershipAdministrationTest::testAChangeWhoseAuditEventCannotBeWrittenChangesNothing -->

**The member for the answer cannot be read:** for `POST` and `PATCH` the
member's name and e-mail address are read from the user account in the
same transaction as the change, before the commit. If that read fails, the
change and its audit event are rolled back and the answer is the same 500.
<!-- verified by MembershipAdministrationTest::testAChangeWhoseResponseCannotBeBuiltChangesNothing -->

**A 500 after the commit.** Everything a change reads and writes, including
its audit event and the data of the answer, happens before the commit, so
an error in any of these steps leaves nothing changed. A 500 can still
follow a saved change in two rare cases: the commit itself ends without a
known result (for example the database connection is lost after `COMMIT`
was sent and before its result arrived), or a step after the commit fails
while the response is finished (for example writing the session at the end
of the request). A client that must know the outcome of a 500 reads the
member list again before it retries; a retried add of a saved member is a
409 `MEMBERSHIP_EXISTS`, a retried removal a 404. The audit log
(`membership.*` events with the `requestId`) shows whether the change was
saved.

## Errors

Checked in this order: 415 and 403 `csrf-invalid` (request origin), 401
(session), 429 (per-user limit), 404 (organization), 403 (permission), 404
(target membership), 422 (body), 409 (conflict). For `POST`, `INVALID_ROLE`
and the other body checks come before the user is looked up, so an invalid
role with an unknown address is only `INVALID_ROLE`.

| Status | Problem type | `errors[].code` | Cause |
|---|---|---|---|
| 400 | `bad-request` | none | the body is not a JSON object |
| 401 | `unauthenticated` | none | no valid session (logged out, expired, disabled user, password changed elsewhere) |
| 403 | `csrf-invalid` | none | origin, `Sec-Fetch-Site` or CSRF token check failed |
| 403 | `forbidden` | none | the actor's role has no such permission, also when the actor was demoted while the request waited for the lock |
| 404 | `not-found` | none | organization unknown or not the actor's; target membership unknown, of another organization or removed; the actor's own membership removed meanwhile |
| 409 | `conflict` | `LAST_ADMIN` | demoting or removing the only active ADMIN, also oneself |
| 409 | `conflict` | `MEMBERSHIP_EXISTS` | the user already has a membership in the organization, active or removed |
| 415 | `unsupported-media-type` | none | a body that is not `application/json` |
| 422 | `validation-error` | `UNKNOWN_USER` (`/email`) | no user has this address |
| 422 | `validation-error` | `INVALID_ROLE` (`/role`) | not exactly `ADMIN`, `MANAGER` or `REP` |
| 422 | `validation-error` | `REQUIRED`, `INVALID_TYPE` | a missing member or one that is not a string |
| 422 | `validation-error` | `UNKNOWN_FIELD` | a body member other than `email`, `role` (`POST`) or `role` (`PATCH`) |
| 429 | `too-many-requests` | none | the per-user API limit (600 requests per minute) |
| 500 | `internal-error` | none | the change, its audit event or the member for the answer could not be written or read (nothing was changed); rarely, a commit without a known result or an error after the commit (the change and its audit event may be saved); read the list again |

## Operational notes and limitations

- **One change at a time per organization.** Every add, role change and
  removal locks the organization row (`SELECT id FROM organizations WHERE
  id = ? FOR NO KEY UPDATE`) and re-reads the actor's membership under the
  lock. Two ADMINs who demote each other at the same time end with one
  ADMIN: the second request finds its actor no longer ADMIN and gets 403
  (removed instead of demoted: 404). The last two ADMINs stepping down at
  the same time also leave one: the second request counts one ADMIN and
  gets 409 `LAST_ADMIN`. Two adds of the same user give one 201 and one 409
  `MEMBERSHIP_EXISTS`. The lock is per organization, and reads take no
  lock and are not blocked.
  <!-- verified by MembershipAdministrationTest::testConcurrentDemotionsLeaveExactlyOneAdmin -->
  <!-- verified by MembershipAdministrationTest::testConcurrentMutualRemovalsLeaveExactlyOneAdmin -->
  <!-- verified by MembershipAdministrationTest::testTheLastTwoAdminsSteppingDownAtOnceLeaveOne -->
  <!-- verified by MembershipAdministrationTest::testConcurrentAddsOfOneUserCreateOneMembership -->
  <!-- verified by MembershipAdministrationTest::testTheActorIsCheckedAgainUnderTheLock -->
  <!-- verified by MembershipAdministrationTest::testAnActorRemovedWhileWaitingIsNotFound -->
  <!-- verified by MembershipAdministrationTest::testALockedOrganizationBlocksNeitherAnotherOrganizationNorItsRefusals -->
- **The operator's `flowcrm:membership:add` takes the same lock**, so it
  waits for a running API change and cannot race an ADMIN's add of the
  same user (`OrganizationLockTest::testTheOperatorAddTakesTheLock`).
- **No bound on the lock wait.** No `lock_timeout` is set; a request waits
  until the lock is free, bounded only by PHP-FPM's
  `request_terminate_timeout` (60 seconds, `docker/api/php-fpm.conf`).
  Membership changes are short, so contention is not expected. A bounded
  wait with its own answer is an open decision in ADR-020.
- **No reactivation.** A removed membership stays `REMOVED`; adding the
  same user again is a 409 `MEMBERSHIP_EXISTS`. Removed members are not
  listed. There is no way to undo a removal through the API or the console.
- **Disabled ADMINs count.** The last-admin rule counts active memberships
  whatever the user's account state. If the only other ADMIN is disabled,
  the enabled ADMIN can still be demoted or removed (also by themselves),
  because the disabled ADMIN is counted; the organization is then left with
  only a disabled ADMIN, and only the operator can help (see Operator
  console). Disabled users can also be added. Whether disabled users should
  count is an open decision.
  <!-- verified by MembershipAdministrationTest::testADisabledAdminCountsForTheLastAdminRule -->
- **Add by e-mail reveals whether an account exists.** An ADMIN can tell an
  unknown address (422 `UNKNOWN_USER`) from an existing one (201 or 409).
  This is bounded only by the per-user API limit of 600 requests per
  minute; there is no lower limit for this route. FCRM-002 BR-02 requires
  the distinction; a dedicated limit is a product decision.
- **Changes apply on the next request.** Roles are not cached: a demoted
  member gets the new permissions, and a removed member a 404, from their
  next request. Their sessions are not ended.
- **Audit and logs.** Successful changes write `membership.added`,
  `membership.role_changed` or `membership.removed` with the actor's user
  ID, actor role `ADMIN`, the organization and the request ID, in the same
  transaction as the change; never an e-mail address. Refusals are not
  audited; they are logged on the `security` channel as
  `authorization_denied`, `tenant_not_found` or `membership_change_refused`
  (reasons `membership_not_found`, `unknown_user`, `membership_exists`,
  `last_admin`). To trace a refusal, search the logs for the `requestId`
  of the problem document.

### Operator console

The operator works in the api container (see
[authentication](architecture/authentication.md#operator-console) for how
to find it). Changes are audited with the actor `platform_operator`.

- Add a member when no ADMIN can (for example after the last ADMIN was
  disabled):

  ```console
  $ docker exec -it "$api" php bin/console flowcrm:membership:add --organization=00000000-0000-7000-8000-0000000000a1 --email=grace@example.test --role=ADMIN
  ```

  It prints the new membership ID. The user must exist
  (`flowcrm:user:create`).
- **Password recovery** has no e-mail flow: the operator sets a new
  password, read from standard input or hidden at a terminal, and every
  session of the user ends:

  ```console
  $ docker exec -it "$api" php bin/console flowcrm:user:reset-password ada@example.test
  ```

There is no console command to change a role or remove a membership; an
ADMIN does that through the API.
